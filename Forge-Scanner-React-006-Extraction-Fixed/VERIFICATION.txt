WHAT WAS FIXED
================================================================
  1. Applications were classified as bank statements.
     classifyDocument tested for wording real application PDFs do not use
     ('requested funding amount' when the forms say 'Requested Financing
     Amount'), and matched bare tokens 'ein' and 'ssn' as substrings, which
     fired inside ordinary words and were worthless as evidence. The phrase
     list now matches the wording the documents actually use. All 13
     applications in the batch are now identified.

  2. A document with no evidence was still labelled a bank statement.
     processDocument hard-coded docType 'bank_statement' for anything that was
     not an application. It now reports what the evidence supports. The full
     statement analysis still runs on every document, so nothing that used to
     extract stopped extracting.

  3. The business name was never recovered from statements.
     pipeline.js set companyNameGuess to null with a comment saying the caller
     would fill it; the caller only tried three labelled patterns that these
     statements never print. The new companyName.js reads, in order: an
     explicit label, an unlabelled line carrying a legal entity suffix, then a
     DBA line. It returns null when there is no evidence and never guesses.

  4. Statements that emit one text item per character were unreadable.
     Row reconstruction joined every item with a space, turning Truist
     statements into '2 3 H U N D R E D  V E N T U R E S  I N C'. Items are now
     joined by the measured gap between them, which rebuilds real words and
     leaves ordinary word-per-item statements byte-identical. This alone lifted
     trusted text from 34 to 39 and deposits from 34 to 39.

  5. Mail-sort barcodes were captured as part of the business name.
     'ACECMKMEIGOCICAAMGOAGCMK A-1 SERVICES GOES ANYWHERE LLC' is now read as
     the company alone. The rule needs both a 16+ character run of capitals and
     four consecutive consonants, so real words like INTERNATIONAL are safe.

  6. Two different company-key rules existed.
     companyAggregator.js and leads.ts each had their own normaliser, and
     neither ignored the legal entity suffix, so '4Bs Entertainment' and
     '4Bs Entertainment LLC' were two leads. There is now one rule in
     companyName.js, used by both.

NOT FIXED — still open, and why
================================================================
  - Six documents have no text layer at all (0 characters). They are the
    Abbaspour statements. OCR recovers them, but OCR is off by default and
    that default is approved behaviour, so it was not changed. Running the
    same batch with OCR on recovers all six. An automatic per-file fallback to
    OCR when a PDF yields no text would fix this permanently; it changes an
    approved default, so it needs your decision.

  - One company still splits into two leads: the statements print
    '1950 ORIGINALS LLC' and the application prints "1950'S Original".
    Those are different words, not a formatting difference, so merging them
    would need fuzzy matching that could merge genuinely different businesses.
    Not done without your say-so.

  - 60 of 61 documents are still 'needs review'. The reasons are counted in
    the batch output: reconciliation mismatch (30), high unparsed line ratio
    (21), reconciliation not possible (13). These are transaction-level
    parsing gaps, which are a separate piece of work from this one.
