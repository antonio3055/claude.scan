================================================================
WHAT WAS FIXED
================================================================
  1. Two of every five statements produced no transactions at all.
     The parser only accepted MM/DD dates at the start of a line. Real
     statements use 01-22-2026, and some print the description first with the
     date beside the amount ("Deposit 650825261202 01-02 1,280.00"). Both
     layouts are now read.

  2. Direction was guessed from keywords, so up to two thirds of transactions
     were left "needs review".
     Statements group their transactions under headings — DEPOSITS AND OTHER
     CREDITS, WITHDRAWALS AND OTHER DEBITS — and that heading is far stronger
     evidence than any word in the description. Direction is now decided by,
     in order: an explicit minus sign, a DR/CR tag, the section, then keywords.
     Every transaction records which of those decided it.

  3. Prose was being read as a section heading.
     "For ATM and Debit Card withdrawals, use the transaction date" is an
     instruction to the reader, and it was flipping the parser into the debits
     section mid-page. Headings are now anchored to the start of the line and
     capped at 60 characters.

  4. Daily-balance tables were becoming phantom transactions.
     "01-02 -432.99 01-14 -20.36 01-23 -160.00" is a balance table, not three
     transactions. Summary tables are now skipped by name.

  5. Cheques listed twice were counted twice.
     Some statements print their cheque table in two different layouts. The
     cheque number now identifies the repeat.

  6. A partly read statement was reported as a reconciliation mismatch.
     The default scan reads 3 pages; the summary totals on page 1 cover the
     whole month. Comparing them said nothing about the document. A truncated
     statement now reports "statement_truncated" instead of a false mismatch.

  7. Scanned PDFs with no text layer produced nothing.
     A PDF whose text layer yields under 50 meaningful characters is an image.
     That one file now falls back to OCR automatically. The regular-scan
     default is unchanged for every file that does have text.

  8. One business was split across two leads by spelling.
     The statements print "1950 ORIGINALS LLC" and the application prints
     "1950'S Original". The company key now ignores possessives and plurals.

================================================================
NOT FIXED — measured, reported, and left alone
================================================================
  RECONCILIATION STILL FAILS ON MOST STATEMENTS.

  Money-in is now exact. Money-out is not. Measured against the banks' own
  totals on three statements:
    ACS Maintenance   parsed debits 28,724.06   statement 25,330.76   +3,393.30
    4Bs Entertainment parsed debits 33,314.77   statement 27,033.39   +6,281.38
    A-1 Services      parsed debits 23,227.52   statement 31,764.93   -8,537.41

  The cause is per-bank table layout on the debit side: cheque tables printed
  two cheques per row, the same cheque table printed twice in different
  formats, and debit categories split across several headings that the summary
  totals combine differently. I built a cheque-table reader for one of these
  layouts, measured it, found it made the numbers worse on a second bank, and
  removed it rather than ship something tuned to one statement.

  Doing this properly means per-bank column layouts, which is a different and
  larger piece of work than this one.

  PAGE LIMIT. The approved default reads 3 pages, and 43 of 48 statements are
  longer than that, so reconciliation cannot even be attempted on them. Raising
  "Regular pages" in Scan Settings to 50 was measured on the same batch:
    completed            1 -> 8
    needs review        60 -> 53
    truncated           43 -> 6
    runtime          61.6s -> 68.2s
  The default was NOT changed, because "regular scan default: 3 pages" is an
  approved rule. It is one field in Scan Settings if you want it.

  60 of 61 documents therefore still read "needs review". That is honest: the
  scanner is telling you it could not verify the arithmetic, and on the debit
  side it genuinely could not.
